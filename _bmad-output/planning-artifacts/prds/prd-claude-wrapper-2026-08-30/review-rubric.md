# PRD Quality Review — Claude Wrapper

## Overall verdict

This PRD is unusually disciplined on framing and traceability: a specific, non-swappable Vision, a single well-used persona, consistent Glossary/ID hygiene, and honest NOTE FOR PM callouts at real tensions rather than safe checkpoints. Its weak point is done-ness clarity — six FRs (the entire Execution Engine and most of the Post-Run Audit Engine) ship with a description but no testable consequences, which is precisely the dimension downstream story creation leans on hardest. Fix that gap and this is a build-ready PRD; as written, an engineer implementing FR-13/14/15/19/20/21 has to infer acceptance criteria from prose.

## Decision-readiness — strong

Trade-offs are named with what's given up, not smoothed over. §9 Cost states plainly "v1 provides visibility only — no hard token/dollar cap and no warn-before-exceed threshold," and §9 Security states Spawned FastMCP processes run with "no additional OS-level sandboxing beyond what file/MCP access the user has explicitly granted" — both real exposures stated without hedging. NOTE FOR PM callouts land at genuine tensions, not decorative ones: FR-4's rejection-handling ambiguity, §6.2's "emotionally load-bearing for the user — revisit at v2 planning, don't let it silently slip further," and §9's flag that v2 multi-user "raises the stakes on this boundary." Open Questions (§11) are actually open — OQ-4 ("What does 'meaningful reduction' mean numerically for SM-1... No target % has been set yet") is a real unresolved commitment, not a rhetorical question answered in the next line.

### Findings
- **medium** Core security-boundary mechanic left unresolved at ship-all-v1 (§9, FR-4, OQ-1) — §9 declares the Permission Manager "the v1 security boundary," yet whether a rejected Pre-Flight item forces re-planning or silently proceeds is unresolved (duplicated as a NOTE FOR PM in FR-4 and as OQ-1). Given §6.1 commits all 22 FRs to ship together, this is a decision a build-readiness reader needs closed, not carried as an open question. *Fix:* resolve at architecture stage before FR-4 is scoped into a story, or explicitly gate FR-4's story on this decision.

## Substance over theater — strong

No persona theater: a single persona (Dana) reused consistently across all three UJs, each driving distinct decisions (task handoff, settings change, mid-run revoke) rather than padding headcount. No Vision theater: §1's Vision is saturated with product-specific mechanism ("flight path," "control tower," "Pre-Flight Permission," checkpoint rollback that "cancels the live stream and cleans up any spawned processes") — it could not swap into another PRD unchanged. No NFR boilerplate: §8's four NFRs carry specific, falsifiable claims ("sub-second perceived delay," "survive a backend crash/restart without corrupting... the last valid checkpoint," "no orphaned processes left running") rather than "must be scalable/secure/reliable." §4.3 names its own differentiator directly ("This is the core differentiator of the product") rather than running a separate Differentiation section for its own sake.

## Strategic coherence — adequate

The thesis is clear and consistently bet on: replace the terminal's opacity with a transparent, approved, auditable agent-orchestration layer, not replace the IDE (§1, §5). Success Metrics validate that thesis rather than measuring activity — SM-1 (token reduction vs. naive baseline) and SM-2 (estimate accuracy) are structurally tied to the core mechanism (context graph / flight path), and counter-metrics are named (SM-C1 guards against starving agents of context to win SM-1; SM-C2 guards against "push" being used to inflate HITL-success optics). SM-3 (weekly retention) is the one metric that reads as generic activity-measurement, though the PRD defends it explicitly as validating "the JTBD is being met, not just tried once" rather than leaving it unexamined.

### Findings
- **low** MVP scope logic asserted rather than argued (§6.1) — "All 7 features and FR-1 through FR-22 ship together in the v1 release" is stated as fact with a supporting note that the 5-phase build order "is the build sequence... not a scope cut," but the PRD never explicitly argues *why* partial delivery (e.g., graph/flight-path without live telemetry) wouldn't still deliver value — it's implied by feature interdependency but not stated. *Fix:* one sentence in §6.1 naming why these FRs are load-bearing as a unit (e.g., "the value proposition is trust-through-transparency; a context graph without live telemetry re-creates the terminal's opacity problem it's meant to solve").

## Done-ness clarity — thin

Sixteen of twenty-two FRs carry an explicit "Consequences (testable)" block engineers can implement against. Six do not: **FR-13** (Live DAG rendering), **FR-14** (Real-time flight path tracking), **FR-15** (Real-time token/time telemetry), **FR-19** (Expected vs. actual metrics summary), **FR-20** (Flight path replay), and **FR-21** (Generated files changelog) each end at a one- or two-sentence description with no acceptance criteria. This is exactly the dimension the rubric says to be unforgiving on, and the gap clusters entirely in the Execution Engine (§4.4) and most of the Post-Run Audit Engine (§4.7) — two of the seven feature groups.

### Findings
- **high** Six FRs ship with no testable consequences (§4.4 FR-13/14/15, §4.7 FR-19/20/21) — every other FR in the doc pairs its description with a "Consequences (testable)" list; these six stop at description only, so "done" for the entire Execution Engine and half the Post-Run Audit Engine is undefined. E.g. FR-13 reads in full: "User can view a DAG graph showing context gained, local files used, and MCP servers (FastMCP-generated vs. pre-provided) for the run" — no bound on what "showing" must guarantee (live vs. on-demand refresh, node-count ceiling, what happens on partial data). *Fix:* add a Consequences block to each, mirroring the sibling FRs already in the same feature group (e.g. FR-13/14 could reuse FR-9's "shown... and replayed" pattern; FR-19/20/21 could reuse FR-22's separation-of-totals pattern).
- **medium** One NFR bound stated as a feeling, not a number (§8, "Planning latency") — "should complete fast enough that the Pre-Flight Permission checklist (FR-4) doesn't feel like a stall before the user can even start reviewing" is the one NFR in §8 that reverts to an adjective ("feel like a stall") where its three siblings all have numeric or crash-survival bounds. *Fix:* give it the same treatment as the Streaming latency NFR's "sub-second perceived delay" — even a rough ceiling (e.g., "under N seconds for a repo of typical size") would make it testable.

## Scope honesty — adequate

§5 Non-Goals and §2.2 Non-Users together give the reader an honest boundary: no multi-model support "now or in a later version," no IDE replacement, multi-user deferred to v2, cloud-hosted deferred to v3 — each with a reason (hosting cost for v3) rather than a silent omission. Three NOTE FOR PM callouts land at genuinely deferred decisions (FR-4 rejection handling, §6.2 multi-user's emotional stakes, §9 trust-model revisit), not at safe checkpoints. Open-items density (4 Open Questions + 3 NOTE FOR PM + 0 Assumptions) is moderate for a PRD that commits all 22 FRs to a single v1 — reasonable, not alarming, though two of the four Open Questions (OQ-1, OQ-3) both trace back to the same underlying gap (the FR-17 status enum not yet distinguishing "failed" from "cancelled," which is also what OQ-1 depends on for FR-4).

## Downstream usability — strong

This is an explicit chain-top PRD ("the working reference for the PM, the architecture and UX skills that follow it, and the epics/stories that will drive development," §0), and it earns that role. Glossary (§3) terms are used identically throughout — "flight," "control tower," "flight path," "Pre-Flight Permission Review," "Stop & Undo" all appear in FRs with the same meaning defined in §3, with the dual technical/UI-facing naming ("Subagent (user-facing: 'flight')") called out once and then respected consistently. FR IDs run FR-1 through FR-22 with no gaps or duplicates; UJ-1/2/3 and SM-1 through SM-5 plus SM-C1/C2 are likewise contiguous. Cross-references resolve: FR-5 cites FR-16, FR-16 cites FR-22, FR-9 cites FR-20, §7 cites FR-8/9/10/16/17/19, §10 cites FR-1/2/12/13/14/15/17/18 — every cited ID exists. Each UJ names its protagonist ("Dana") inline with enough context (existing vs. new repo, mid-project, mid-run) to be read standalone.

## Shape fit — adequate

This is a single-operator developer tool with meaningful, differentiating UX (live graph, real-time telemetry) — UJs with a named protagonist are load-bearing here, and the PRD uses exactly one persona across three UJs rather than manufacturing personas per feature, avoiding both over- and under-formalization. The brownfield reference is accurate: §6.1's claim that the architecture doc's "5-phase roadmap (Core Engine → FastMCP Bridge → Visual Canvas → Node Inspector → Post-Run Audit)... is the build sequence... not a scope cut" was checked against `docs/claude_wrapper_system_architecture_and_plan.md` §8 and matches phase-for-phase. New vs. existing-repo UJ entry states are distinguished explicitly (UJ-1's two Entry states; FR-8's "Existing-repo runs include codebase files as graph nodes; new-repo runs do not").

## Mechanical notes

The roundtrip is technically satisfied (0 inline = 0 indexed) but unverifiable as written — a reader can't tell whether discovery genuinely surfaced no lingering assumptions or whether they were resolved so cleanly no trace was worth keeping. Low weight since the claim is plausible and the PRD is otherwise disciplined about NOTE FOR PM/Open Question hygiene elsewhere.
- **Title still marked provisional** — H1 reads "# PRD: Claude Wrapper *Working title — confirm.*" (line 9). Harmless but should be closed out before this is called a final draft.
