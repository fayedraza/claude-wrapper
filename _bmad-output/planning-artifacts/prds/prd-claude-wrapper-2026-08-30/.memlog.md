- (decision) Target users: solo developers and teams using Claude Code-style agentic tools who want an AI-driven dev workflow in place of the raw terminal.
- (decision) Core problem: agents going off-script with low visibility, plus token-maxing/waste; product goal is to use graph-based retrieval to match the best-fitting docs/context to a prompt and minimize token usage while preserving output quality.
- (decision) Source architecture doc: docs/claude_wrapper_system_architecture_and_plan.md (supersedes deleted docs/claude-wrapper-architecture.md), including images/user-journey-flow.png and images/technical-architecture-diagram.png.

- (decision) Stakes: launch-grade (full rigor, length driven by FRs/concerns).
- (decision) Working mode: Coaching path, Vision + Features entry point (capability-first, fits dev-tool with 6 predefined capabilities).
- (decision) Concern scan: token/cost efficiency (primary driver), process isolation & permission security (FastMCP spawn, file/MCP grants), real-time reliability (WebSocket/SSE streaming, interrupt/checkpoint correctness), developer-product surface (Pydantic schemas, MCP tool contracts). Adapt-In sections selected: Cross-Cutting NFRs, Constraints & Guardrails (Cost, Safety, Security), Developer Products cluster (API Contracts/Public Surface, Language/Runtime Targets). Platform: web (Next.js), noted briefly, no dedicated section needed.
- (decision) Context Matcher (graph-based context retrieval) is a v1 capability, not a future bet. Each agent/subagent gets a source graph (MCP servers, local docs, existing Claude context) divided into subtopic nodes by the Meta-Planner; LangGraph executes the nodes. 'Flight path' = the route from source to destination node that covers all needed context while minimizing token spend ('gas') and staying within an efficient token-usage pattern ('wind').
- (decision) Terminal replacement is full, not partial: user does not use a terminal for Claude Code-style agent work in v1 -- all input/output (including subagent questions) happens in-UI. Product is a companion to the IDE though, not a replacement for it: user still sees generated files, run commands, etc. in their IDE.
- (assumption) Aesthetic direction: user wants a colorful UI, explicitly not a dark-terminal aesthetic. Flagged to addendum.md for downstream UX spec.
- (decision) Context graph/flight path applies per-agent to BOTH the main orchestrator agent and every subagent, not subagents only.
- (decision) Vision section locked (v1 draft): covers Settings natural-language config, per-agent context graph + flight path, pre-flight permission approval, real-time token drift visibility, in-UI HITL question answering (no terminal), checkpoint rollback, and Post-Run Audit. IDE remains source of truth for files/commands; Claude Wrapper owns only the agent conversation.
- (decision) Initialization branches on repo state: if .claude/ exists, Settings Router reads/builds on it; if not, it creates it fresh.
- (decision) Context graph nodes include the existing codebase's own files as subtopic sources, not just external docs/MCP/Claude context -- codebase files are part of the flight path too.
- (decision) New-project sequencing: main orchestrator agent acts as 'control tower' sequencing subagent 'flights' -- one agent's task starts (takes off) before dependent agents start, rather than all firing simultaneously. Glossary terms: flight = agent/subagent run, control tower = main orchestrator agent, flight path = execution route, cancelled flight = cancelled agent.
- (decision) Two additional Key User Journeys requested by user: (1) updating Settings via natural-language prompt post-init, Claude determines which .claude/ files to touch; (2) updating permissions (add/revoke) for already-granted files/MCP servers outside the Pre-Flight review.
- (decision) Control-tower sequencing (main agent gates/releases subagent 'flights' based on dependency readiness) is universal -- applies on existing repos and new repos alike, not just new-project init.
- (decision) Settings updates (UJ-2) require explicit user approval before .claude/ files are written, same gating pattern as Pre-Flight Permission review.
- (decision) Revoking a file/MCP permission (UJ-3) takes effect immediately, including cutting off an agent that is actively mid-run using that resource -- ties to the same abort/cleanup mechanism as Stop & Undo (cancel stream, terminate spawned processes).
- (decision) Glossary correction: Subagent and Flight are the SAME concept, not two -- 'Subagent' is the technical/internal term, 'Flight' is the user-facing term for the same agent run. Main orchestrator agent is NOT a flight; it is the control tower.
- (decision) A flight has two terminal outcomes: completed or cancelled -- once cancelled it does not resume. If a flight runs into trouble, the user is notified and can either push it (give redirect/guidance input to get it back on track) or cancel it.
- (decision) Glossary wording: use 'agent' (not 'flight') in the terminal-outcomes/trouble-handling sentences for consistency; 'flight' stays as the UI-facing alias noted once, not reused as the operative noun.
